# EMS Scout 批次时间线治理工作台设计

## 状态

设计阶段。本文档用于指导后续实现，不包含代码实现细节，也不改变现场数据。

## 目标

将现有“历史数据管理 / 数据对比 / 质量审计”长页面改造成面向数据管理员的批次治理工作台。管理员应能在一个上下文中完成：

- 按时间追溯采集批次及其处理结果；
- 判断批次是否具有完整、可信的质量和实时证据；
- 将历史批次与当前数据或其他批次进行对比；
- 在有明确影响预览和保护规则的前提下恢复或删除历史快照；
- 在批次被删除后仍能解释本机发生过的治理操作。

本设计采用“时间线作为默认视图、表格作为清理视图、详情面板作为统一操作入口”的组合，而不是纯图形时间轴。

## 非目标

- 不改变 EMS 采集链路、实时匹配规则或 Excel 导出契约；
- 不新增云端服务、远端日志或现场数据同步；
- 不引入图表库、事件总线或复杂工作流引擎；
- 不把实时详情缺失伪装成有效的集控锁定状态；
- 不提供无确认的“一键删除全部历史数据”。

## 用户与核心任务

主要用户是集中复核、对比和清理历史批次的数据管理员，而不是只查看当前设备状态的现场操作员。

主要任务按优先级排列：

1. 找到需复核、实时证据缺失或质量异常的批次；
2. 查看批次范围、卡片数、证据完整性和问题原因；
3. 对比当前数据与历史快照，决定是否恢复；
4. 清理不再需要的历史快照，同时确认不会影响当前设备数据；
5. 回溯恢复、备份、异常标记和删除等治理动作。

## 信息架构

### 页面入口

审计导航仍保留，但默认内容改为“批次时间线”。顶部提供：

- 刷新；
- 时间线视图；
- 表格视图；
- 清理模式；
- 打开数据管理。

默认优先显示当前活动批次和需复核批次，不隐藏 `needs_review`。

### 顶部摘要

摘要区只显示支持管理员决策的指标：

- 当前数据批次；
- 待复核批次；
- 缺实时证据批次；
- 可恢复批次；
- 可清理批次；
- 最近一次审计时间。

每个数字必须能作为筛选条件使用。没有数据时显示“无批次”，不能用 `0` 掩盖读取失败或状态筛选错误。

### 筛选栏

筛选条件包括：

- 时间范围；
- 楼栋；
- 状态；
- 数据来源；
- 是否当前批次；
- 是否存在实时快照；
- 是否存在质量问题；
- 是否允许删除；
- 批次号、`run_key`、备注关键词。

筛选条件改变后，时间线、表格、摘要指标和详情面板保持同一数据集，不产生各自独立的隐藏筛选。

## 时间线视图

### 批次节点

每个节点显示：

- 完成时间；
- 批次编号和 `run_key`；
- 楼栋范围；
- 卡片总数；
- 基础质量状态；
- 实时快照状态；
- 当前 / 历史标记；
- 可执行操作。

节点按导入或完成时间倒序排列。当前批次固定使用明显的“当前数据”标识，但不依赖颜色表达唯一含义。

### 生命周期事件

已有批次字段可推导以下事件：

- 采集完成；
- 导入 SQLite；
- 质量审计；
- 实时审计；
- 异常标记；
- 恢复为当前数据；
- 恢复前自动备份。

删除事件需要记录最小本地操作元数据。删除后的原始设备快照和证据文件不再恢复到时间线中，只保留“已清理”事件及其统计信息。

### 视图密度

时间线不展示每张设备卡片。批次节点只展示摘要，设备级问题放入详情面板或数据管理页，避免几千条设备记录把治理页面变成第二个数据表。

## 表格与清理模式

### 表格视图

表格提供固定列：

```text
选择 | 批次 | 完成时间 | 楼栋范围 | 卡片数 | 质量 | 实时证据 | 状态 | 操作
```

状态、质量和实时证据使用可读文本与徽标同时表达。表格支持排序、筛选和单行操作。

### 清理模式

进入清理模式后显示复选框、已选数量、预计释放空间和“删除历史快照”按钮。支持：

- 删除选中的历史批次；
- 删除指定日期之前且符合删除条件的历史批次。

当前批次、正在运行的批次和恢复链中仍被引用的必要备份默认不可选。系统不得提供无条件删除全部历史数据的按钮。仓储层必须再次校验当前批次和引用关系，不能只依赖 UI 的按钮禁用。

## 详情面板

选择时间线节点或表格行后，右侧详情面板展示四个区域：

### 批次摘要

- 批次编号；
- `run_key`；
- 完成、导入时间；
- 来源、版本、操作者；
- 楼栋范围；
- 卡片数量及开机、关机、离线、未知统计；
- 当前 / 历史 / 恢复备份关系。

### 证据状态

分别展示：

- SQLite 历史快照；
- 实时详情快照；
- 基础质量报告；
- 实时质量报告；
- JSON / NDJSON 关联文件。

“文件存在”不等于“证据有效”。实时快照缺失、批次号无法绑定、字段无效或报告过期时，必须明确显示原因。

### 对比结果

默认提供“与当前数据对比”，并允许选择另一历史批次。显示：

- 历史卡片数与当前卡片数；
- 新增、缺失、字段变化数量；
- 按楼栋汇总；
- 可定位到设备数据页的问题列表。

### 操作区

提供：

- 恢复为当前数据；
- 删除历史快照；
- 标记异常 / 取消异常；
- 查看质量报告；
- 打开数据管理。

## 删除契约

### 术语

界面统一使用“删除历史快照”。该操作删除的是选定批次的历史记录和关联证据，不是当前设备数据。

### 保护规则

- 当前活动批次不可删除；
- 采集任务运行中不可删除相关批次；
- 目标批次不存在时不执行任何删除；
- 多选中包含不可删除批次时，默认整体阻止并列出原因；
- 删除失败时事务回滚，不能留下部分删除结果。

### 删除确认

确认对话框必须列出：

- 批次编号、`run_key`、完成时间；
- 楼栋范围和历史卡片数；
- 实时详情条数；
- 将删除的报告和数据文件；
- 不会删除的当前数据、备注、标签和人工匹配规则。

单批次删除要求管理员确认批次编号。批量删除要求确认已选数量和日期/状态条件。取消确认不产生副作用。

### 删除结果

删除成功后：

- SQLite 历史表和关联实时详情在同一事务中删除；
- 关联本地证据文件按现有安全路径校验后删除；
- 当前设备数据、备注、标签和人工匹配规则保持不变；
- 刷新摘要、时间线、表格和当前选中项；
- 写入最小本地删除操作记录。

数据库和文件系统不共享原子事务，因此删除采用两阶段语义：数据库记录删除必须整体提交或整体回滚；文件删除在数据库提交后执行。若文件被占用或权限不足，数据库不会回滚，也不能报告为完全清理，系统应保留“待清理文件”状态、列出残留路径并允许后续重试。该状态不得重新暴露已删除文件的内容。

删除操作记录不得包含设备原始字段、实时点位内容或文件正文，只保留批次标识、操作时间、操作者、数量和结果。

## 恢复契约

恢复前必须展示批次对比结果，并明确全量恢复或部分楼栋恢复。恢复在一个事务中完成，当前数据先生成恢复前备份，时间线随后显示恢复关系。

恢复失败时保留原当前数据和原历史批次，不产生半成品备份或错误的“已恢复”事件。

## 批次标识规则

`collection_runs.id` 是内部技术主键，分配后永久保留在本地身份登记表中，即使历史批次删除也永不复用；展示批次号 `run_no` 才允许回收空缺。因此技术 ID 可用于数据库关联，但不能单独承担对用户展示的业务身份。

界面和本地操作记录必须同时使用：

- 展示用 `run_id`；
- 不可变的 `batch_uid`；
- 不可变的 `run_key`；
- 操作事件的唯一标识。

时间线排序、删除记录和恢复关系使用 `batch_uid`、`run_key` 或操作事件标识；`run_no` 仅用于显示。这样即使旧 `run41` 被删除、未来再次生成新的展示 `run41`，两次事件也不会被混淆，且数据库技术 ID 仍保持单调递增。

## 数据流与边界

```text
SQLite collection_runs / run_* 快照
              │
              ├── 批次目录与状态查询
              ├── 时间线事件投影
              ├── 详情面板证据状态
              └── 对比 / 恢复 / 删除命令

本地质量报告、实时审计报告、JSON、NDJSON
              │
              └── 只读关联与有效性展示，不上传远端
```

页面只消费应用层批次治理模型，不直接拼接 SQLite 结果。删除和恢复仍由批次仓储统一执行，避免 UI 自己维护级联删除逻辑。

第一阶段不增加新的采集数据格式。只有删除操作记录需要最小新增本地结构；若现有批次字段足以生成事件，则不重复存储派生事件。

## 建议的应用层模型

后续实现可增加以下只读模型：

- `RunTimelineEvent`：事件标识、事件类型、时间、关联批次；
- `RunEvidenceStatus`：快照、报告、实时证据及有效性原因；
- `RunGovernanceDetail`：批次摘要、对比摘要、可执行操作和删除影响；
- `RunDeleteImpact`：将删除的记录、文件和禁止删除原因。

已有 `ICollectionRunRepository.DeleteAsync`、`RestoreCurrentAsync` 和 `CompareCurrentAsync` 应继续作为写操作边界，不在页面代码中复制 SQL。

## 错误处理

- 数据库读取失败：页面显示“批次读取失败”，摘要不显示伪造的零值；
- 质量报告缺失：显示“未找到报告”，不等同于质量通过；
- 实时快照缺失：显示“实时证据缺失”，集控锁定状态保持不可用；
- 文件被占用：数据库删除结果保持完整，关联文件进入“待清理”状态并可重试；
- 并发刷新导致选中批次消失：清除选中项并提示数据已刷新；
- 删除或恢复取消：不改变状态，不写成功记录。

## 测试与验收

### 批次读取

- 默认列表包含 `completed` 和 `needs_review`；
- 当前批次、历史批次和恢复备份的状态徽标正确；
- 无批次与读取失败在 UI 上可区分；
- 按楼栋、状态、日期、实时证据筛选后所有区域数据一致。

### 时间线

- 事件按时间和不可变标识稳定排序；
- 恢复与备份关系可追溯；
- 删除后的事件不再泄露已删除设备原始内容；
- 删除后复用相同 `run_id` 不会覆盖或混淆旧操作记录。

### 删除

- 当前批次不可删除；
- 单批次和批量删除都需要确认；
- 删除影响预览数量与实际删除数量一致；
- SQLite 事务失败时所有记录保持不变；
- 关联文件删除失败时不会留下数据库半删除状态，并会明确报告残留文件；
- 删除后当前设备数据、备注、标签和人工匹配规则仍存在。

### 回归

- 现有实时快照优先绑定测试继续通过；
- 现有最小可用批次号分配测试继续通过；
- .NET 全量测试、Node 自检和安全测试通过；
- Release 构建和 MSIX 安装验证通过。

## 分阶段交付

### 第一阶段：可用治理核心

- 修正 `needs_review` 默认筛选；
- 时间线默认视图；
- 批次详情面板；
- 单批次安全删除；
- 当前批次删除保护；
- 删除影响预览；
- 时间线 / 表格视图切换。

### 第二阶段：批量治理

- 清理模式；
- 多选删除；
- 日期和状态条件清理；
- 可删除性和证据完整性筛选；
- 本地删除操作记录。

### 第三阶段：深度追溯

- 恢复分支可视化；
- 两个历史批次之间的对比；
- 质量问题直接定位到数据管理；
- 保留策略和空间占用提示。

## 设计取舍

纯时间轴视觉上直观，但批次数量增长后不适合清理；纯表格高效，却无法表达恢复和备份关系。因此默认使用时间线建立上下文，清理任务切换到表格，所有操作集中在详情面板。

本设计优先复用现有 WinUI、SQLite 仓储和报告读取服务，不增加外部依赖。只有在现有字段无法表达删除审计时，才增加最小本地操作记录结构。
